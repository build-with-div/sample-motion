# Q13: deterministic animation capture in pinned Chromium

Milestone M2. This is the platform plan's question Q13: which way of driving
time in pinned Chromium gives byte-stable captures for package-level
comparisons? The decision of 13 November 2026 was to measure byte stability
across runs before choosing between begin-frame control and virtual time.
This document is that measurement.

## Setup

- **Tool:** [`tools/chromium_capture_stability.py`](../tools/chromium_capture_stability.py).
  It reuses Div's harness (`tools/accountability/run_all_pixel_comparisons.py`
  at Div `92ea25a0`) for the CDP client and Chromium's font environment.
- **Browser:** Chrome for Testing 147.0.7727.50 linux64, Div's pinned
  oracle binary, with the census flags (`--headless --disable-gpu
  --no-sandbox`). The viewport is 200 × 120 at DPR 1, set through
  `Emulation.setDeviceMetricsOverride`.
- **Machine:** WSL2 on Windows 11, 24 threads, load average 0.3–1.4 when
  the runs started. Measured 13 November 2026.
- **Command:**

  ```sh
  python3 tools/chromium_capture_stability.py DIV_CHECKOUT CHROME_DIR 10
  ```

  A full run takes about 90 s.
- **Animation:** one 60 px box animated from `translate(0px, 0px)
  rotate(0deg)` at opacity 0.2 to `translate(100px, 0px) rotate(45deg)` at
  opacity 1, over 1000 ms with linear easing. It is driven three ways, as
  the packages drive it:
  - `css`: a CSS `@keyframes` animation (tailwindcss-animate, Radix);
  - `waapi`: `element.animate()` (Motion, AutoAnimate);
  - `raf`: a `requestAnimationFrame` loop writing inline style (GSAP,
    react-spring, Motion's main-thread values).
- **Samples:** at t = 0, 100, 250, 500, 750 and 1000 ms after the start.
  Each row of the results is 10 runs, and every run is a fresh browser
  launch.
- **What is recorded per sample:**
  - the SHA-256 of the decoded RGBA and of the PNG;
  - the animation time the page reported at capture: iteration progress ×
    1000 ms, or the rAF loop's elapsed time;
  - whether the capture equals the **nominal reference**, the `paused` CSS
    capture of the first run at the same t;
  - whether it equals a `paused` CSS capture made at the **time the page
    itself reported** (204 such reference captures were made).

## Methods

| Method | How time is driven |
| --- | --- |
| `paused` | CSS: `animation-delay: -t` with `paused`, one navigation per t. WAAPI: `pause()` then `currentTime = t`. A rAF loop cannot be seeked, so `raf` does not apply. |
| `virtual-time` | Load on real time, then `Emulation.setVirtualTimePolicy` `pause`. Start the animation, advance a budget to each t, wait for `virtualTimeBudgetExpired`, capture. (Pausing before navigation stalls the load: 0 of 3 pages loaded in 15 s.) |
| `virtual-time-main` | The same, with Chromium's deterministic-mode switches other than begin-frame control: `--disable-threaded-animation --disable-threaded-scrolling --disable-checker-imaging --run-all-compositor-stages-before-draw`. |
| `begin-frame` | `--deterministic-mode --enable-begin-frame-control`. A page target is created with `enableBeginFrameControl`, then `HeadlessExperimental.beginFrame` is called at frame times start + t, with the screenshot taken by the frame itself. |
| `raf-pump` | `raf` only. `requestAnimationFrame` and `performance.now` are replaced before the page's scripts. The oracle calls the queued callbacks at 60 Hz frame times up to each t, and at t, then captures. Main-thread flags as `virtual-time-main`. One discarded warm-up capture is made after load. |

## Results (10 runs per row)

Distinct RGBA hashes across the 10 runs. Distinct PNG hashes were equal in
every row. The full table, with each t and both reference columns, is
regenerated by the command above.

| Method | css | waapi | raf | Matches the reference |
| --- | --- | --- | --- | --- |
| `paused` | **1** at every t | **1** at every t | n/a | 60/60 nominal (css), 60/60 (waapi) |
| `virtual-time` | 2–3 per t | 2–3 per t | 4–5 per t | css/waapi: 0/10 at the reported time for every t. raf: 10/10 at the reported time for t = 100, 0/10 from t = 250. |
| `virtual-time-main` | 3–6 per t | 5–8 per t | 5–7 per t | css/waapi: 0/10 at the reported time for t ≥ 250. raf: 10/10 at the reported time for t ≥ 100. |
| `begin-frame` | not available | not available | not available | `'HeadlessExperimental.beginFrame' wasn't found` (all 30 runs) |
| `raf-pump` | n/a | n/a | **1** at every t | 60/60 nominal |

What the reported times show:

- **Virtual time starts the animation one frame late.** CSS and WAAPI
  report 83.3 ms at a 100 ms budget, and 983.2–983.4 ms at 1000 ms.
- **Virtual time does not pace rAF frames.** After a 1000 ms budget, the
  rAF loop had seen 349.9–366.7 ms of frames with threaded animation and
  249.9–349.9 ms on the main thread. The frame count per budget varies
  between runs.
- **With threaded animation, the pixels are not the page's state.** CSS and
  WAAPI captures never equal the reference at the page's own reported
  time once t ≥ 250. The compositor-thread animation is sampled on its own
  clock.
- **On the main thread, CSS and WAAPI report the same time in every run**
  (233.3 ms at the 250 ms budget, for example), yet give 3–8 distinct
  captures. The captured frame is not the one the probe saw.
- **The first capture of a new page can be stale.** Without the warm-up
  capture, `raf-pump` gave 2 distinct captures at t = 0, with 6 of 10
  matching the reference. Div's harness confirms its captures with a second
  read for the same reason (`render_chrome`).

## Conclusion

For Chromium 147 as pinned (the full Chrome for Testing binary, new
headless mode, `--disable-gpu`):

- **Virtual time is rejected.** No row is byte-stable across runs, and its
  time does not reach rAF or compositor animations.
- **Begin-frame control could not be measured.** The pinned binary does
  not expose `HeadlessExperimental.beginFrame`. Chromium documents
  `enableBeginFrameControl` as supported by chrome-headless-shell only, and
  the oracle has no chrome-headless-shell. Adding one,
  `chrome-headless-shell` 147.0.7727.50 from Chrome for Testing, would be a
  second oracle binary. That is a decision for the engine tools track, and
  the methods below do not need it.
- **What is byte-stable, measured:**
  - **Animations created by WAAPI and CSS:** seek them paused. This is
    1 hash per t over 10 runs, and equals the reference 60/60. WAAPI was
    measured through `pause()` and `currentTime`, CSS through a negative
    delay. Seeking a CSS animation through `getAnimations()` is the same
    operation, but it was not measured here.
  - **rAF-driven code:** the oracle pumps rAF at explicit frame times,
    with a warm-up capture after load. This is 1 hash per t over 10 runs,
    and equals the reference 60/60.
- **Package comparisons therefore use seek plus pump.** At each frame k,
  the oracle:
  1. calls the page's rAF callbacks with the frame time;
  2. pauses every animation in `getAnimations()` and sets its current time
     to the frame time minus its start;
  3. captures.

  Div's side does the same on its headless clock, with rAF (R1) at the same
  frame times. Motion uses WAAPI and rAF together, so this combination is
  measured with the first port (M3) before any package result is reported.

What this does not test: the pump replaces Chromium's own frame
scheduling. Comparisons made this way check what is rendered at given frame
times, not when Chromium produces frames or in what order it runs rAF
callbacks against other work. That ordering is the job of WPT's
update-the-rendering tests, through T3 script translation.
